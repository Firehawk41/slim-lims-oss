## Bugs (confirmed; with the fix and its guard test)

**T-1 fixed the same day** (Jamie: "Fix T-1"). The guard runs the app behind uvicorn's own
`ProxyHeadersMiddleware` with every proxy trusted, as Render does; without the fix the attacker's 21st try is
let through (401 where 429 is due). Still to check once on Render: that its proxy is one hop (a login's
`X-Forwarded-For` holding the client's address last). The Docker image keeps `--forwarded-allow-ips='*'` for
the deferred Caddy setup; there `TRUSTED_PROXY_HOPS=1` must be set too (`.env.example` says so).

| # | Where · lens | Finding | Fix | Guard |

| T-1 | Login throttle ↔ Render's proxy · 9 (plan T3) | **The per-address login limit can be dodged, and turned on someone else.** Render and Docker start uvicorn with `--proxy-headers --forwarded-allow-ips='*'`. With every proxy trusted, uvicorn 0.54 takes the **leftmost** `X-Forwarded-For` entry as the client (`ProxyHeadersMiddleware`: `if self.always_trust: return x_forwarded_for_hosts[0]`). That entry is whatever the client sent: Render's proxy appends the real address after it. So a script that sends a new `X-Forwarded-For` with each try is never held by the 20-per-address limit (password spraying across accounts). One that sends someone else's address locks that address out of logging in for 15 minutes. The per-account limit (5) still holds. Without `--proxy-headers`, every visitor would share Render's address and be locked out together: the other half of the prediction. | **Built:** `security.client_address`: the `X-Forwarded-For` entry `TRUSTED_PROXY_HOPS` from the right (`render.yaml`: 1; default 0, the socket's peer), used by both login steps for the throttle only; `--proxy-headers` stays for the scheme (Secure cookies, `url_for`). Also `test_auth.py::test_t1_the_address_is_the_proxys_entry`. | `test_auth.py::test_t1_a_forged_forwarded_for_neither_dodges_nor_frames_the_login_limit` |

## Refuted / checked sound

- **Plan T1** (`upgrade_lab` and migration 0018 per lab): refuted. `upgrade_lab` runs the app's Alembic upgrade with the lab's URL, whose `search_path` puts the lab's schema first (`labs.with_schema`). The unqualified `CREATE TABLE`, `CREATE FUNCTION` and `CREATE TRIGGER` in `models.append_only` therefore land in the lab's schema, not public, and the version table is the lab's own.
- **Plan T2** (`empty-public` and the sweep miss new tables): refuted. Both drop a whole schema (`DROP SCHEMA … CASCADE`); there is no table list to forget.
- **Plan T4** (MFA skipped only for ASSERTED): refuted. `accounts.mfa_required` exempts personas and the API token only. `/login` refuses personas. Choosing a persona clears the session first, so a real user in the middle of MFA setup who switches is simply a persona now, and is held for setup again when they log in.
- **Plan T5** (a visitor's reference refresh reaching the shared lab): refuted. `/reference` refreshes the `reference` dependency, which is the visitor's own lab's cache (`get_reference` → `labs.reference_for`); guarded by `test_refdata.py::test_l2_…`.
- **Plan T6** (0018 → 0017 on Postgres): refuted by reading. `DROP FUNCTION … CASCADE` takes both triggers with it, then the index and table go. `test_migrations.py` runs downgrades on SQLite only; Postgres is untested.
- **Plan T7** (`SECRET_KEY` unset in development): refuted. Development falls back to a fixed key (`config._DEV_SECRET`), so sessions, CSRF and sealed MFA secrets survive a restart. Production refuses to start without one, and Render generates and keeps it (`generateValue`).
- The bearer token reaches `LIMS_ROUTES` only (`test_lims_contract.py`); every router carries CSRF; the OSS guard is unchanged.
- Lenses 1, 2, 5, 6, 7, 10: nothing new. Lens 4: see T-3. Lens 9: T-1.
