# App review: the seams between modules, 2026-10-30

The second app review (the first: `REVIEW_2026-10-28.md`), after slim-prep and slim-quality were wired in,
with `REVIEW_CHECKLIST.md`. Every seam: host ↔ slim-data, host ↔ slim-prep, slim-prep → slim-data (handoff),
host ↔ slim-quality, host ↔ invoicing V5, host ↔ slim-domain and the report engine, and the per-visitor labs
around them all. Vulnerabilities and optimizations. Measured on a seeded Postgres demo with the audit log
(3,364 entries): every page 0.02–0.3 s; `cli verify` replays all 29 result versions, chain intact.

## For decision: all four built (Jamie, "1-4 please"; D-116…D-119)

| # | Seam | Finding | Recommendation |
|---|---|---|---|
| R1 | Every module · 8 | Every module is installed from `@main` of every other (the host's `pyproject.toml`, Render's build, slim-prep's own dependency on slim-data). A merge in one repo changes what the next deploy runs, untested against the host; a deploy can't be reproduced. | Pin each module to a release tag (or commit) in the host; bump them in a PR, so CI tests the exact set that deploys. |
| R2 | slim-prep → slim-data · 8 | slim-prep calls slim-data's persistence (`register_batch`, `correct_prep`, `get_batch`) inside the host's transaction: module rule 2 ("modules never import each other") is broken here by design (D-95), and slim-prep depends on slim-data's internals. | A small handoff API in slim-data's service layer (register a prepped batch, send its correction) that slim-prep calls, or the host composes (as for slim-quality); D-95's behaviour unchanged. |
| R3 | Invoicing V5 · 7 | I1 is guarded in the host, but V5's `write_csv` itself still writes formulas, for any other caller. | Fix at the source: V5 writes text cells safely (its repo isn't in this session). |
| R4 | Host ↔ invoicing · 4 | Recording a payment updates the invoice row in place (`paid_on`): history only in the Postgres audit log, as TRs were before D-104. | Payments as append-only rows, like `tr_versions`. |

## Checked and sound (nothing new)

- **Who may see it (1):** every module page is staff-only; quality pages need a quality capability; run files,
  the audit and the register are staff-only; customers reach only their own TRs, reports and invoices.
- **Who may do it (2):** one identity across modules (an analyst named in a file resolves to the host user's
  id, so four-eyes compares like with like); the LIMS token may still set report statuses (deliberate, D-99);
  personas hold only their CSV capabilities; quality decisions and closes are a manager's.
- **State says the truth (3):** wiring slim-quality set no status by hand (Jamie's re-check rule); an amended
  report after invoicing leaves the TR invoiced (forward only) and V5 bills what any report showed.
- **Whose clock (5):** module dates are aware instants shown in the lab's zone; SQLite's naive TR history times
  are taken as UTC.
- **Untrusted input (6):** series ids, NC impact refs and forms are checked against what the server knows;
  slim-data's and slim-quality's field lengths line up.
- **Output escaping (7):** reports and charts escape every value; run files download as attachments with a
  sanitised name; the run list was already guarded.
- **Sessions and auth (9):** the new routers carry CSRF (the sweep covers them).
- **Demo isolation (10):** a lab's schema comes from the signed session and is checked; shared state is
  reference data only.

Accepted: series keyed by the instrument's and material's names as files give them (a rename starts a new
series); every quality page recomputes the charts from the whole history (0.2–0.3 s on the demo; cache by
data version before years of real data); the audit page re-verifies the audit chain (0.27 s at 3,364
entries; on demand before a large log); two uploads of one file at the same instant: the second is a 500
instead of "imported before" (rare; the file is never imported twice).
