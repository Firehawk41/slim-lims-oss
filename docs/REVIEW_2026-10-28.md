# Architecture review, 2026-10-28

A step back after slim-prep (Jamie: "edge cases and vulnerabilities … architectural weaknesses"; a sandbox
demo, so security is weighed for what it teaches and what it protects, not as production). Each item that gets fixed becomes a decision in the owning repo. Fixed so far: A1 (D-100), A2 (D-99),
A4, A7, A8, A10 (D-101), A3 (D-102; on for Render), A6 (D-103), A5 (D-104).

## A. The app (slim-lims as a whole)

Ranked by how much they weaken the design.

| # | Weakness | Where | Suggested fix |
|---|---|---|---|
| A1 | **Any staff member is a user administrator.** An analyst can create customer accounts for any customer (and so read that customer's requests, results and invoices) and **deactivate anyone, supervisors included** (`toggle_user_active` has no role check). Only raising a lab role is supervisor-only. | `routes.py` admin routes | User administration for supervisors only (later: an admin role); nobody deactivates a higher role. |
| A2 | **TR status can be set by hand, apart from the facts.** The status form lets staff move a TR to *complete report* with no report issued, or *invoiced* with no invoice; a cancel doesn't reach slim-data or slim-prep (results can still be released, a cancelled TR's prep batch can still be sent). D-71 automates the forward moves, but the manual path bypasses them. | `domain/workflow.py`, status form, `services.change_status` | Statuses that stand for a fact (report issued, invoiced) are set only by the action that makes the fact; cancelling checks the modules (refuse, or tell them). |
| A3 | **The public demo is writable by anyone, for good.** `DEMO_PERSONAS` on Render gives every visitor the supervisor persona: sign-offs, imports, prep, invoices. Nothing resets it; the seed only adds what's missing. One visitor can leave the demo full of junk or half-finished states for the next. | `render.yaml`, seed | A scheduled demo reset (drop and re-seed), or personas that can't touch the seeded scenarios. |
| A4 | **No limit on login attempts.** Real staff accounts exist next to the personas on Render; passwords can be guessed at full speed. | `auth.login` | A small per-account and per-IP limit with a delay. |
| A5 | **The host's own records are mutable; the modules' are not.** slim-data and slim-prep are append-only with triggers; TRs, users and invoice rows are updated in place. On Postgres the audit log records the changes, but on SQLite (dev, tests) nothing does, and "what did this TR say on day X" can't be read back except from the log. | `models.py`, repositories | Decide deliberately: either TR history as events (like slim-data) or accept "audit log only, Postgres only" and say so in the spec. |
| A6 | **Access scoping fails open.** `repo.list(customer_id=None)` means "all customers"; a customer user is only kept to their own by the DB constraint that every customer has a `customer_id`. A future code path that loses the ID would show everything. | `services.list`, `board.board` | Scope explicitly: a customer always filters, `None` for a customer raises. |
| A7 | **Report HTML is trusted.** Issued reports are shown with `|safe`; both renderers escape every value today and the CSP blocks inline script, but the app relies on each renderer to stay correct. | `templates/*/report*.html` | Keep the CSP (it is the backstop); add a test that customer-typed text (sample name, contact) comes out escaped in both renderers. |
| A8 | **Every module trusts the clock it happens to read.** "Today" is the lab's date for TRs (`lab_today`), but slim-prep's screens use the server's date and UTC (see B4). | prep screens | One `lab_today()` / lab-time helper used by every module's host code. |
| A9 | **The board loads at most 500 TRs per status** and silently omits the rest. | `board.py` | Fine for the demo; page or summarise before real volume. |
| A10 | **XML from instruments is parsed with the standard library.** No external entities (so no XXE), and the 1 MB cap bounds expansion, but a DOCTYPE is still accepted. | slim-data `qtegra/1` | Refuse a DOCTYPE in the export. |

Checked and sound: session login rotates the session and CSRF token; CSRF on every router (JSON via
header); CSP without `unsafe-inline`; HSTS in production; 1 MB body cap with or without Content-Length;
bcrypt with a timing-equalised unknown-user path; open-redirect-safe `next`; the slim-lims bearer token is
limited to three routes and never falls back to the session; customers are refused staff pages and see
only their own TRs, reports and invoices; deactivating a user ends their access on the next request.

## B. Module level (slim-prep and its seams with slim-data), found the same day

| # | Weakness | Fix |
|---|---|---|
| B1 | slim-prep never checks a sample against its TR (exists, received, ordered this analysis); `send_to_results` registers it in slim-data below its reference checks. | A TR port for slim-prep (P-02 planned it); check on record and on send; the chemical comes from it too. |
| B2 | A correction can change a batch's method or analysis (hidden fields, API body). | A correction keeps code, method and analysis. |
| B3 | The on-screen correction drops a cup's second spike line silently. | Show every line, or refuse the grid for such a batch. |
| B4 | The prep time is the save time; dates come from the server, not the lab's time zone. | Enter the prep time (bounded); lab-local dates (A8). |
| B5 | An instrument file can add samples and spike amounts to a batch slim-prep registered. | slim-data: a prepped batch takes no new samples or spikes from a file (D-99). |
| B6 | Batch codes are shared between modules with nothing reserving them. | A clear refusal on collision; a prep code pattern. |
| B7 | slim-prep doesn't record identity source (personas look like logins); "who" is a UUID for standards but initials for batches; "poured out by" is free text. | slim-data's `Actor` (with identity source); pour-out from the staff list. |
| B8 | Free-text batch codes reach the CSV run list (formula injection) and its download filename. | A code pattern; neutralise cells starting `= + - @`. |
| B9 | A correction is checked against the rules current now, not the batch's own. | Keep the batch's rules version; moving to new rules is a recorded step. |
| B10 | A crafted grid field (`sample_x`) gives a 500. | Parse defensively, 422. |

Noted, not worth fixing now: list pages load every version of every record; `batches_using` makes one
lookup per batch; the run list groups matrices by the customer's chemical text rather than the matched
chemical ID (comes with B1).
